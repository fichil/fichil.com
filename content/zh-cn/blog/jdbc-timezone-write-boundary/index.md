一笔运输订单在测试环境成功创建，列表里的创建时间却比接口接收时间早了 14 小时。对照接入日志和订单表，发现偏差在入库时就已出现。页面读取的是数据库里已有的值。

第一次修复通过了驱动和订单列表验证。后来一次发布替换了连接配置，偏差再次出现。这个复发让我们补上了另一个检查点：部署包最终会交给数据库驱动什么配置。

## 用相同驱动复现时间换算

JDBC 是 Java 访问数据库的接口。我们用服务实际运行的 MySQL 驱动 Connector/J 8.0.20 和现有连接配置建立只读对照，把同一个时间值作为查询参数交给驱动，也就是测试时间参数绑定。这样能观察驱动传出的值，无须创建新订单。

接入服务依赖驱动自动解释数据库返回的 `CST`。在本例中，驱动按北美中部时区解释这个缩写。冬季是 UTC−6，业务使用的上海时间是 UTC+8。驱动按错误的时区换算参数后，数据库收到的时间比预期早了 14 小时。已配置上海时区的另一条连接没有偏差。给接入服务的对照连接显式指定 `serverTimezone=Asia/Shanghai`，偏差同样消失。

后续探针还覆盖了夏季。相同配置在夏季样例上偏差为 13 小时。历史校正需要先确认哪些记录受影响、当时的换算差值是多少，不能把冬季观察到的数字套到所有日期。

## 检查真正运行的连接配置

修复覆盖同步接口和消息监听服务。第一次同步修改了运行目录和两个部署包里的 JDBC 配置。后续版本从环境配置源重新生成连接参数时，时区设置没有被保留。

第二次修复一并更新了发布时填充连接参数的配置源，并在停服前检查两个部署包内的最终配置。这样即使源文件只有环境占位符，发布检查仍能发现替换后缺少时区的情况。部署后，再用实际运行的驱动和配置回测当前时间、跨日时间和夏季时间。

参数用法取决于驱动版本和时间字段类型。迁移到 Connector/J 8.0.23 或更新版本时，应对照新版的时间处理选项，并用实际 Java 参数类型和数据库字段重新测一遍。 [MySQL Connector/J 时间处理文档](https://dev.mysql.com/doc/connector-j/en/connector-j-time-instants.html)

## 单独修复已经写错的数据

显式设置连接时区只影响此后的转换。已有订单按受影响的主记录和明细逐条确认，再在同一个事务里锁定并核对原值。创建时间按已验证的差值校正。原修改时间仍等于原创建时间时，才同步校正这两个值。已经发生的后续业务操作保留原修改时间。

提交前逐项回读新值，确认非时间字段保持不变，并保留修复前快照供精确恢复。提交后通过订单查询核对历史值，后续修复又直接在列表页面复核。新写入的时间换算由部署后的只读参数探针验证，验证范围限于开发和测试环境。

排查类似问题时，先找出时间值第一次发生改变的位置。把同一个值沿接入日志、实际驱动、数据库和查询接口核对一遍，再把检查放进能改变这些配置的发布流程。
