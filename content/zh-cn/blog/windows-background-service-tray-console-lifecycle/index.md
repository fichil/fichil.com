一个 Windows 应用的后台业务保持健康，本机恢复控制台却没有在启动后出现。同步仍在继续，健康接口也能响应，现场操作人员仍缺少清晰入口，无法方便地打开控制台执行本机恢复。

让控制台窗口一直开着也会引入风险。关闭管理窗口不应停止后台业务。升级还需要替换版本目录，而隐藏控制台可能继续占用文件，或正处于敏感操作中。

本次修复把三个职责交给不同所有者：后台业务进程、交互式托盘控制台，以及负责选择活动版本的稳定启动器。启动、唤醒、升级和回退通过一套小型协作协议连接。

## 一个应用可以包含两个生命周期

后台业务与控制台的可用性要求不同。

控制台最小化、关闭或显式退出后，后台业务仍需继续。它负责同步、定时处理和持久状态，其健康状态通过服务边界检查，不能依赖窗口是否存在。

控制台属于交互式用户会话。它提供本机恢复操作、打开网页管理入口、查看日志和本机凭据恢复。它的可用性同时依赖已登录的桌面会话与 Windows Shell。

把两个角色放进同一个进程，会让每个窗口动作都影响业务。关闭按钮可能停止后台处理；部署器可能持续等待一个不可见窗口；Shell 重启后，进程仍活着，托盘入口却可能消失。

修复后的进程归属如下：

```text
后台业务进程
  └── 持久业务与数据

交互式控制台
  └── 本机界面与恢复

稳定启动器
  └── 活动版本跳转
```

这个划分也让故障描述更准确。托盘图标缺失不能直接说明后台业务中断，服务健康也不能证明本机恢复入口可达。

## 把稳定跳转层放到版本目录之外

便携部署常把每个修订版放进独立目录。桌面快捷方式如果直接指向某个版本，激活新版本或回退后就会失效。

本次修复在安装根目录增加稳定启动器。它读取活动版本记录，再启动对应控制台。人工启动携带“显示窗口”意图，自动启动携带“后台运行”意图。首次配置始终显示窗口，避免应用把唯一设置入口隐藏起来。

桌面快捷方式和交互式启动任务都使用同一个稳定路径。新版本激活时，活动版本记录与稳定入口一起更新；回退时，两者同时恢复到上一版本。快捷方式与计划任务无需知道具体版本目录名。

稳定层保持很小：它只选择已经验证的本地版本，并保留调用方的启动意图。它不复制业务数据，不改写认证状态，也不替部署器决定版本是否可上线。

## 重复启动只唤醒一个控制台

每个安装目录、每个交互式用户会话只允许一个控制台实例。后续启动向现有进程发送激活请求，然后自行退出。人工激活会显示窗口；后台启动请求不会擅自改变已经运行控制台的当前状态。

这个规则消除了几类歧义：

- 多个托盘图标同时提供互相冲突的操作；
- 多个本机凭据恢复对话框并行出现；
- 一个进程退出，另一个进程仍占用同一版本文件；
- 重复启动任务表面成功，实际留下多个隐藏控制台。

关闭或最小化主窗口会保留托盘入口。显式“退出控制台”只结束控制台，后台业务仍由独立所有者管理。Shell 重启后，控制台收到 Shell 恢复通知并重新创建托盘入口。托盘创建失败时，控制台显示主窗口，避免恢复入口静默消失。

## 把升级做成协作交接

升级器需要让交互式进程在有限时间内释放版本文件。直接结束控制台可能打断已开始的凭据恢复、导入或其他本机操作。

控制台因此提供仅限本机的退出通知。升级时存在三种结果：

1. 空闲状态下正常退出，部署器继续切换活动版本；
2. 受保护操作执行期间报告忙碌，当前版本继续运行；
3. 无法协作时返回明确失败，部署器在激活前停止。

新版本通过健康和数据检查后，部署器更新稳定入口，并在交互式会话中启动新控制台。激活失败时，先恢复上一版本和对应启动目标，再重启控制台。

旧版本无法识别新的退出通知。首次升级保留旧启动器已有的关闭方式，形成兼容边界。这样，第一次升级不会依赖只有新版本才具备的能力。

## 凭据恢复继续留在本机

控制台缺失会直接影响本机恢复。修复后的流程仍在交互式控制台接收新值，调用已有本机认证恢复机制，并撤销旧浏览器会话，无需重启后台业务。

系统没有新增远程管理接口。启动脚本、日志和部署记录都不保存秘密。升级协议只询问控制台能否退出，不接触恢复输入。

这个边界让部署与认证分别演进。新版本可以重启控制台而不重置凭据，本机恢复也可以撤销浏览器会话而不停止同步。

## 分开验证窗口行为与发布行为

隔离桌面检查覆盖自动隐藏启动、人工可见启动、重复启动唤醒、关闭到托盘、最小化到托盘、显式退出、首次配置可见，以及真实 Shell 重启后的托盘恢复。托盘初始化失败时，可见窗口回退也通过验证。

打包与部署演练覆盖从旧版本升级、托盘控制台运行期间升级、受保护操作忙碌、控制台已停止、发布切换中断、浏览器认证交接、回退和重连。

受保护流水线构建并部署了精确审阅版本。发布后检查确认线上版本一致、两个服务边界健康、交互式会话中的控制台进程存活、持久偏好没有变化。发布验收不需要发送测试消息，也没有调整业务开关。

一个视觉边界需要明确保留：自动化确认了生产控制台进程和交互式启动任务，没有在最终生产桌面目视检查托盘图标。进程存活与任务状态可以证明运行边界，无法替代对 Shell 最终渲染结果的图像级确认。

## 限制与可复用结论

这套设计依赖已有的 Windows 交互式会话。它不配置自动登录，也没有把托盘控制台改成 Windows 服务。没有交互式会话的环境需要选择其他恢复入口。

协作退出还依赖准确的忙碌边界。新增敏感操作时，必须登记其受保护区间；遗漏登记后，升级仍可能在不安全时刻到达。

可靠的 Windows 桌面 Agent 适合设置三个明确所有者：后台进程负责持久业务，交互式控制台负责本机恢复，稳定启动器负责选择发布版本。单实例唤醒、Shell 重启恢复、可见回退与协作退出把它们连接起来，同时保留各自独立的生命周期。
